# 需求功能文档编写器

以项目无关（project-agnostic）方式生成或更新需求/功能文档，支持：
1. 模块索引文档（总览 + 阅读顺序 + 统一规则）
2. 版本需求文档（目标/范围/步骤/验收）
3. 对已有文档做增量更新（状态、决策、变更记录）

## 何时使用

当用户提出以下诉求时使用：
1. 新建需求文档
2. 新增版本规划（`v1`、`v2`、`v3` 等）
3. 将零散想法整理成可执行方案
4. 统一现有文档结构并补齐验收标准

## 先做最小发现

在写作前，先检查目标仓库已有文档风格：
1. 命名规范（如 `feature.md`、`feature_v2.md`）
2. 章节结构与标题层级
3. 状态语义（planned/in-progress/done）
4. 变更记录日期格式

若仓库没有明确规范，再使用本 skill 内置模板。

## 必填输入槽位

先补齐以下信息（仅问缺失项）：
1. 主题/模块名
2. 文档类型：`index` 或 `version`
3. 版本号（仅 `version` 需要）
4. 当前状态（`Planned`、`In Progress`、`Done`）
5. 一句话目标
6. 范围约束（必须做 + 明确不做）

## 文档类型判定

1. 需求是“模块路线与文档组织”时，用 `index`。
2. 需求是“某一版具体实现”时，用 `version`。
3. 请求不明确时：
   - 若模块无总览文档，先建 `index`。
   - 否则优先创建/更新 `version`。

## 固定写作流程

1. 确认目标文件路径与文档类型。
2. 从仓库上下文或用户输入提取约束。
3. 套用模板骨架。
4. 填写具体、可验证内容。
5. 对未拍板项写明假设与默认值。
6. 追加当天变更记录（`YYYY-MM-DD`）。
7. 输出检查清单并标记通过/未通过。

## 输出契约

输出必须包含两段：
1. `## 文档草案`（完整 Markdown）
2. `## 验收检查清单`（`[x]/[ ]`）

若关键信息不足，先输出：
1. `## 待确认问题`（最多 3 条）
2. 然后仍给出带 `TODO:` 标记的草案

## Index 文档要求

必需章节：
1. `# <主题> 文档索引`
2. `## 文档目的`
3. `## 阅读顺序`
4. `## 统一规则`
5. `## 变更记录`

规则：
1. 索引文档保持高层抽象，不写低层实现细节。
2. 阅读顺序遵循“基线 -> 近期 -> 远期”。
3. 统一规则应是跨版本长期有效约束。

## Version 文档要求

基础章节：
1. `# <主题> V<版本号>（<标题>）`
2. `## 状态`
3. `## 背景`
4. `## 范围`
5. `## 非范围`
6. `## 待确认问题`（决策完成后可移除）
7. `## 实施步骤`
8. `## 验收标准`
9. `## 变更记录`

已完成版本可补充：
1. `## 实现说明`
2. `## 影响文件/接口`
3. `## 验证结果`

规则：
1. `Done` 状态必须附日期。
2. `实施步骤` 必须按执行依赖顺序。
3. `验收标准` 必须可观察、可测试，且仅覆盖当前需求变更范围（未变更内容不纳入本次验收测试）。

## 质量规则

1. 优先使用编号列表，便于追踪。
2. 避免“优化/提升”等不可验证表述。
3. 明确区分：需求、设计决策、未决问题。
4. 语言保持简洁、可执行。
5. 涉及复杂流程、边界条件或非常规实现的实施项，需在代码中补充“为什么这样做”的注释；避免仅复述代码字面行为的注释，并保持注释与实现同步。

## 回退策略

1. 仓库规范冲突时，优先遵循仓库本地规范。
2. 若仓库无规范，使用本 skill 模板。
3. 请求过大时，先产出 `v1` 草案并写明假设。
